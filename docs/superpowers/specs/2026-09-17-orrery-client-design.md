# The orrery client in Talon: observations from chat, mail and the calendar

Status: drafted 2026-09-17 against orrery's design spec of 2026-09-16 (`nisfeb/orrery`, `docs/superpowers/specs/2026-09-16-orrery-design.md`). Decisions in section 2 are the owner's.

## 1. What this is

Orrery keeps a model of one person's world on their ship: bodies, immutable observations about them, and actions. The ship runs no AI and never sees text. Clients do the triage. Talon is the client with the most context, since it holds the user's chat, mail, calendar and contacts on one device, so Talon pushes into orrery whatever it can derive, and a larger model reads the state back on the ship's side.

Two pipes feed orrery from Talon. The structural pipe turns facts Talon already knows for certain into observations, with no model involved. The triage pipe turns what people say into claims about the world, and that needs a language model, which runs on the device.

## 2. Decisions

- Talon writes with a minted key, one per install, never with the owner cookie. The audit trail names the client, and policy's sensitive attributes never reach it.
- Talon pushes every structural fact it can, from contacts, chat, mail and the calendar. When auspex and the calendar push their own facts from the ship, the matching sources leave Talon. Source ids are chosen so that handoff is a no-op, not a duplicate.
- Triage runs locally by default on every platform. A cloud provider may be used for triage only when the user opts into it explicitly, in its own switch, with the consequence stated. Sending every message to a cloud provider is against the privacy principles of Urbit. A frontier model reading the orrery state on the ship's behalf is not, because that state is claims and pointers, never the text.
- Text never leaves the device for the ship. An observation's source is a pointer that Talon can open, and its value is a claim.
- The best model a device can run is the one it uses. The floor exists so that every supported device works, not so that every device gets the floor. A newer system with better on-device model access uses that access, and the experience is never lowered to what the oldest supported version can do.

## 3. Not fighting the ship

The ship is the source of truth and the owner's reconcile pass consolidates what clients get wrong. orrery-utils' `docs/writing-a-client.md` is the rule set every client shares, and Talon follows it:

1. **Nothing is said twice.** Every message read, every occurrence written, every person and event decided is remembered in `orrery_sent`, keyed per ship. The ship answers `existing` for an observation it already holds, but a body upsert makes the body again, so a replay used to recreate whatever reconcile had just merged away. A pass that fails records nothing, so it is free to say the same things again.
2. **Resolve before creating, and a hit is the thing itself.** `GET /resolve?q=` by the calendar's own id first, which reconcile keeps as an alias of what it built and which every body this client makes carries: an exact hit there is the event, whatever else is true of it. Then by the title, which is weaker: a series takes an exact `activity` by that name, and a one-off takes an exact `situation` only when it is still open and starts within a day of this occurrence, since a closed one is a past occasion and one on another date is another occasion sharing a title (two "Nutcracker Mandatory Parent Meeting" evenings, October and December, are two situations). A word or prefix match is never the event. A hit of kind `activity` makes the event an occurrence of it (`last` at the occurrence's start, `next` for the one after); a hit of kind `situation` gets the facts; a hit of kind `person` is that person, whatever name the message used. Only a miss makes a body: an `activity` for something that repeats, carrying the UID and the title variants as aliases, a `situation` for a one-off. A new activity also says who holds it, but only for a calendar this ship keeps itself: on one another ship shares, whose activity it is is that ship's to say.
3. **The schedule is not the fact, and a status is not the clock.** A time ahead is a schedule: `starts` and `ends`, dated when this install learned it, because a row dated in the future is hidden until then. A time behind is what happened: `started` and `ended`, each at its own moment. Nothing is said in the past tense about something still ahead, and an occurrence written as a schedule is said again in the past tense once it is over, which is what the `:s` and `:f` marks on the remembered occurrence are for. Who is in it and where it is are dated when we read them, for the same reason the schedule is. A situation's status is only ever `closed` or `cancelled` from this client: `open` dated after a close reopens what the retire pass shut, `upcoming` and `over` are read off the times, and the calendar writes no status at all, with one exception: an event this install wrote that the calendar no longer keeps, whose start is still ahead, gets one `status: cancelled` row, `at` the moment it was noticed and the uid as its source. Its body is never deleted. Gone means absent from the full listing, not the window, which also loses an event moved past its edge; one already behind is over and left to retire, and a calendar that went away as a whole is not taken as its events called off.
4. **Event time in `at`.** `started`, `ended`, `last` and `next` are anchored to the event, never to the reminder or the clock, so a reminder cannot outrank a close.
5. **Everything through the key.** The owner cookie is used for three things only: asking whether orrery is there, minting this install's key, and revoking it. Every write carries `Authorization: Bearer` and lands in `/tr/log` as `talon/<platform>`.
6. **No local cache of bodies is pushed.** What exists is read from `GET /state` each pass. A person already on the ship under another name is used by id; `normalizeTitle` and `samePerson` are ported from orrery-utils so sameness is decided the way reconcile decides it. A body the ship has is taught the names it lacks and nothing else: an upsert carrying aliases and no name unions them and leaves the ship's own name where it is, which is how a new nickname, or the new title of a renamed event, arrives without remaking a body the owner may have merged. Names alone are never sent for a body the ship does not have, because that would come back as a hollow body named after its own slug.
7. **Sensitive facts keep their two names.** `health` and `income` are the ship's, kept from keys by policy. Whether this client may write them is the ship's to say and not a constant in the client: orrery 13 serves a key minted with `sensitive: write` a schema that names them, and the parse follows that schema. Talon's key is not minted that way today, so both are dropped; a claim that reaches for another name for either is dropped whatever the scope, since under another name it would land in plain sight of every key.
8. **A status is a circumstance, not a feeling.** A person's `status` is what they are doing or dealing with, as an onlooker would put it: "on jury duty", "stranded, waiting for a tow". The prompt says so, carries two worked examples, and repeats whatever the ship itself says its attributes mean, read from the `notes` block of the state view where the ship is new enough to have one. Feelings are given a sink, `mood`, which the parse throws away, so that "want to scream" has somewhere to go that is not a status. Tlon's own status field is a social one, where most lines are a joke, an in-joke, an emoji or a quote, so it is not sent as a fact at all: the line goes through the triage like any other text, once per wording, and what the reader makes of it waits in the tray.
9. **A message is read with the ones before it.** "yes, at 8" says nothing alone. The model is shown the last four messages of the same conversation, marked as being for reading only, and the claims are held to the words of the new message: the subject must be named in it or be its author, a value must be found in it, and a status, which is a paraphrase by design, must share a word with it. Mail is one message per call, because a mail carries its own quoted history. A call's lines are a conversation like any other.
10. **Everyone an event names is in it.** A title is certain of some names ("Adelaide- Ballet/Tap", "Rose and Linus- Opti Sail", "Magnus Birthday") and only guesses at a leading word, which counts when the ship already keeps somebody by that name, so a production, a team or a place stays what it is. A description names whoever the ship already knows, written with a capital: "bring Linus's helmet" is Linus, and "rose garden", "grace period" and "will call" name nobody. The reading is `names_in` from the owner's own reconcile pass, ported, so client and ship name the same people. A person the ship lacks is created, but only by the pass that makes the event, never by one that re-says it, or a rename would resurrect somebody reconcile had merged away. Two of the places a person can be named are not open to this client: the calendar's rows carry no attendee list and no organizer field, only a name, a note, a location, a colour and tags, so an attendee is known only where the title or the description says so, and the organizer is named only as the owner of a calendar this ship keeps.
11. **Replay-safe by construction.** The pipe can be turned off and on, or run again from nothing, and the ship ends up the same.
12. **A dismissal carries the owner's reason, and only theirs.** The note on a dismissal rides into the on-ship generator's next prompt, where it is read as the owner's taste. The action dialog asks "Why not? (optional)" with the guide's two examples ("just the event", "I always do this") a tap away; the Actions page's Dismiss offers the same, no reason, or the dialog to say more; a reply to the brief carries the owner's own words ("dismiss A3, it's just the event") and none when they gave none. Talon writes no reason of its own: a due change's replacement dismisses with no note, since the owner still wants the thing. Talon writes no note of its own at all now that the todo list is the ship's. At most 500 bytes, cut on a character.
13. **Writes in batches, and the generator is the owner's.** Every write wakes the on-ship generator. A pass gathers what it will say and sends it as batched `observe`s at its end, one pass at a time; answers write a few rows inside the generator's twenty-second settle; the beacon and the fifteen-minute net are reads. Talon never writes the generator's documents and never calls `POST /generate`, which is the owner's run-now on the page.

Said once is not said for ever: an event people edit has to go through the pass again. The decision remembered for `cal:<cal>/<uid>` carries a hash of the event as against its times, over the title, the note, the place, the cadence and the tags, so a rewritten description or a new location is noticed on the next pass and what the event is gets said again. A time is caught the other way round: an occurrence this install wrote that the window no longer holds has moved or been called off, and its rows are retracted by id, read from `GET /api/body/<id>`, because the ship keeps the latest `at` of the rows it has and a meeting moved earlier would otherwise go on reading as the time it used to be at. Each occurrence is remembered with its end as well as its start, so the rows at both anchors come back off together, and the occurrence is forgotten so the new time is written as new. Only inside the window, which is the one stretch of time the client can see the truth of.

**Only the schema's words.** Before a batch goes up, a row on an attribute the key's schema view does not list for that kind is not written and the log names it: an unlisted attribute sits outside the owner's vocabulary and no reader of the ship sees it. `last-contact` on a person and `transcript` on a situation are the pipe's own and are in ricsul's schema (added 2026-09-19); a ship that lacks them gets neither.

## 4. The structural pipe

| Talon data | Body | Observations | source kind and id |
|---|---|---|---|
| A contact in the person's own book (never a ship merely seen; the profile cache holds thousands) | `person/<ship slug>`. Name is the nickname, else the word name. Aliases: nickname, @p, word names | none. The status line is read by the triage, not sent as a fact | `contacts`, `<ship>` |
| A DM or group DM from anyone; a channel post only from someone in the book | none new | `person/x.last-contact` = the day, `at` = the start of that day | `talon-dm` for a DM, `talon-chat` for a channel post, id `talon://chat/<whom>?id=<post>` |
| A mail message | `person/<ship>` for from and to | `person/x.last-contact`, `at` = sent capped to now, since the author's clock is untrusted | `mail`, `talon://mail/<thread>` |
| A calendar event that happens once | `situation/<date>-<title>`, the day it happens in this device's zone the way the ship names its own, made only when the ship resolves nothing, with the UID as an alias, and a `person/<name>` for anyone its title names whom the ship lacks | `starts` and `ends` while it is ahead, `started` and `ended` once each has passed, `location`, `participants` = me and everyone the title or the description names, at conf 85 | `calendar`, `<cal>/<id>` |
| A recurring calendar event, from the occurrences the window holds | one `activity/<title>` for the series, made only when the ship resolves nothing, with the UID and title variants as aliases, and a `person/<name>` for anyone its title names whom the ship lacks | `cadence`, `schedule`, `location`, `participants` = me and everyone the event names, `organizer` = me on a calendar this ship keeps, and one `last` per occurrence at its own time, plus `next` | `calendar`, `<cal>/<id>` |
| A calendar event with a location | none | `person/me.location = <place>` at the start until the end, conf 60 | `calendar`, `<cal>/<id>` |
| A call whose transcript was published, 1:1 or a party line | `situation/call-<time>`, name from the transcript's title, and each speaker's person as the pass resolves them (the ship's own body by @p or name, `person/<ship>` only when it has none), taught the handle and never renamed; the facts are made inside the pass for that reason | `started`, `participants` = me and every speaker, `transcript` = the Lattice address; `person/x.last-contact` for each speaker | `talon-call`, the transcript's `urb://` address |

**The ship keeps the todo list, as of orrery 34.** Talon kept orrery's tasks and the calendar's todos in step for as long as no one else could: it made the todo for an approved task, ticked it when the action went done, took it away when the action was refused, filed a hand-typed todo as an approved task and linked it. The ship does all of that itself now, on its own executor fiber, and two mirrors over one list place twice and tick twice, so Talon keeps none of it (client guide rule 11, rule 13). The same goes for putting an approved `calendar` action on the calendar: the ship makes the event, tags it `orrery`, and moves the action to done.

What Talon still does with actions is one thing: it is the executor for `message` actions whose `via` is `chat`, which it sends as an Urbit DM (rule 14). Telegram goes through the ship's bot and mail through auspex, both from the ship, the moment the owner approves. A claim the ship holds answers `claimed by ship` and is left alone.

The calendar pipe reads the other way and is unchanged, with one thing to keep true: a row carrying `meta.orrery`, an `orrery-` uid or the `orrery` tag is orrery's own and never becomes a situation, and todos never do whatever they carry. The ship writes those rows now, which is what makes the rule load-bearing rather than tidy.

A body slug for a person is the @p without its sig, with `--` for a comet's separators. The ship is identity, so resolve matches it exactly, and a share is addressed by it.

Every observation carries `by = talon/<platform>` (the key's identity, forced by the ship anyway), `conf` 100 for a structural fact, and `at` from the event, never from the clock of submission.

## 5. The triage funnel

Most of what Talon sees is group chatter about nothing in the user's world. The funnel drops it cheaply before the model runs, and the model sees only candidates.

1. **Scope.** DMs, threads the user is in, mentions, mail addressed to the user, and channels on a user allow-list. The transcripts of the user's own calls, 1:1 and party lines, enter too, read back from Lattice by the address the call's situation carries. Nothing else enters.
2. **Names.** The scoped state view, cached by `rev` and refetched when the beacon moves, gives every body with its aliases and ship. A message that names a body, by alias or by ship (the contact map already resolves nicknames and word names), is a candidate. This is deterministic and instant, and it uses orrery's own model as the prior: the more bodies the user has, the better it gates.
3. **Pattern.** Where the platform has an embedder (Android and desktop today), a nearest-centroid test between a few "claim about the world" prototypes and chit-chat prototypes, with the observations the user confirmed as a growing positive set, the way `Highlights.kt` scores against bookmarks. The gate learns the user's pattern with no training. A platform without an embedder runs gates 1 and 2 only.
4. **Extraction.** The candidate and the scoped body list (names, aliases, current attributes; sensitive ones are already stripped by the key) go to the local model with a grammar that admits only the answer shape: observations with subject, attr, value, at, until, conf, and any new bodies. Talon validates before submitting: attr charset and length, refs resolve to known bodies, conf capped at 80 for anything model-asserted. A refused attr is dropped and remembered as sensitive.
5. **The person.** A Noticed tray in Talon, like the Requests section, shows each proposed observation with its source message: confirm or discard. A per-kind threshold lets confirmed kinds submit on their own once the user trusts them. Retract from the same tray. New places, things and situations are created only through the tray at first; people are created freely, because a ship is identity.

The two models are named for what they are for, not for where they run. The **frontier model** writes summaries, answers in the assistant and carries out what the analyst proposes. The **private model** reads messages. Either may be a service or a server on a machine the person owns, and either may want a key or none, so both are a provider or an address, a model name and an optional key. The private model's blank address means whatever this device can run itself, which is the ladder below. Both live in the AI configuration that syncs, so a server set up on the computer is known to the laptop, and the switch that lets the frontier model read messages instead is a preference beside them, off until it is chosen.

## 6. Local extraction: a ladder, best rung first

Every device runs the best local model it has access to, chosen at runtime, and falls to the next rung only when the one above is absent. The contract is the same on every rung: the same prompt, the same answer shape, the same validation, the same tray. What differs is the model behind it. The bottom rung is a shared runtime that works everywhere, and it is there so that no device is left out, not as the target.

| Platform | Top rung | Middle | Floor |
|---|---|---|---|
| iOS | Apple Foundation Models on iOS 26 and an Apple Intelligence device: the system model, guided generation as the grammar, no download | llama.cpp with the largest model the device's memory allows, Metal | llama.cpp, a 1B to 2B model at 4-bit |
| Android | Gemini Nano through AICore where the device has it (the ML Kit GenAI prompt API; verify its status at build time, it has been pre-release) | MediaPipe LLM Inference running Gemma 3n on the GPU or NPU on devices that carry it (Gemma's bundles are gated behind Google's terms, so this needs a signed download, not an in-app fetch) | MediaPipe LLM Inference with LiteRT's ungated Qwen2.5 1.5B bundle, GPU where the phone has it, else CPU |
| macOS | Apple Foundation Models on macOS 26 and Apple silicon, through a small Swift helper the JVM app talks to over stdio | llama.cpp with Metal and a 4B to 8B model, sized to memory | llama.cpp, 1B to 2B |
| Linux and Windows | A local server already running on the machine (Ollama or LM Studio at their default ports), which is local by definition and may hold a model far larger than anything Talon would download | llama.cpp with Vulkan or CUDA where a GPU is present, and a 4B to 8B model sized to memory | llama.cpp, 1B to 2B on the CPU |

Rules of the ladder:

- A rung is used only after it has passed the extraction fixtures at least as well as the rung below it, on that platform, in CI or on the device the first time it is enabled. A faster model that answers worse is not a better experience.
- The floor's model is sized to the device too: the shared runtime picks the largest of a short list that fits memory with headroom, so a flagship phone on the floor still runs a better model than a budget one.
- Detection is per device and per launch, and Settings shows which rung is in use, by name, with the reason the higher rungs are not (no Apple Intelligence, no AICore, not enough memory). A user who wants a rung the device could run but has not downloaded gets the download offered there.
- Models are downloaded on first use, never bundled, and the download is offered rather than started silently on mobile data.
- Desktop rungs that load native code run in a probed child process like `EmbedderProbe`, so a runtime that crashes takes nothing with it.
- Every rung the device lists is local. The cloud extractor is a separate switch beside the pipe on the Apps page, off, with its consequence written beside it, and needs a key set under AI. While it is on it is the top of the ladder, because the person chose it knowing what it costs.

The grammar guarantees valid JSON on the llama.cpp rungs and Apple's guided generation does the same; on rungs without constrained decoding the answer is validated and retried once, then dropped. A bad answer is therefore a wrong claim that meets validation and the tray, never a parse failure.

A capability flag, `isLocalTriageSupported`, gates the funnel's model stage per platform, and the copy says when it is off. Nothing in gates 1 to 3 needs a model.

Extraction runs in the background: on Android under WorkManager when charging or idle, on desktop and iOS while the app is open, with a per-day budget so a busy channel cannot run a phone flat.

## 7. Auth and transport

- **Key.** At setup Talon mints its own key with the owner cookie: `POST /apps/orrery/api/clients` with name "Talon on <platform>", `by: talon/<platform>`, scope every kind and action kind the owner's `GET /schema` lists, write true, and `sensitive: "write"`, so the owner's reply to the brief can file `health` without the key ever reading it back. Each run the key's own schema view is measured against the owner's: one missing a kind, an attribute (sensitive names show only to a key that may write them) or an action kind is replaced and the old one revoked. A key the ship will not read the state for is left alone, since that is the owner revoking it. The token is stored beside the session, and every orrery request carries it as a bearer, never the cookie. Revoking it on the ship stops Talon within a second.
- **Availability.** `OrreryApi` probes like `AuspexApi` and `CalendarApi`: no Grubbery, no orrery, and orrery present are three different states, none an error. The Apps page gets an orrery row.
- **Batches.** 50 bodies and 200 observations per observe, with per-item answers. Talon keeps an `orrery_sync` table: a cursor per source (last sentMs per whom, last mail thread time, calendar rev) and the ids it submitted. Observation ids are content hashes, so a resend is a no-op and the cursor can be conservative.
- **Backfill.** Opt-in, over a chosen window, after the switch is turned on. Incremental thereafter from the live feeds Talon already runs: chat facts over the channel, the mail poll, the calendar poll.
- **Reads.** The scoped state view for the funnel and for showing state in Talon, refetched on the beacon.

## 6a. The decision model: a gate before the reader, a check after it

TypeSafe's Jev, through OpenRouter's decisions route (`typesafe/jev-1.13`, provider `{"zdr": true}` always, the OpenRouter key Talon already has), answers typed questions: output free, input $0.042 a million tokens, under half a second. It is off until the owner turns it on under Settings > AI > Orrery, since every message the reader would read then goes to OpenRouter. The route, the model and the threshold are settings, not code: the route is alpha. `orrery-utils` `common/analyze.py` (`Decider`, `gate`) and `telegram/bot.py` are the reference.

- **The gate.** Before the reader, one `noul` question per free-text message, `worth_reading`, with the state `analyze.gate` builds: the message, the sender's body id, the earlier texts of the conversation (rule 9's window) and every body the key sees as `id | name | aliases`, the ones the message names first, then people. The reference sends 80; sending all 173 of ricsul's measured the same answer time at about eight cents more per thousand messages, and a cut at 80 could drop the one person a message is about. Below the threshold (0.3 to start) the reader is not asked and the log says "not read"; at or above, it reads as before. A gate that errors or takes 30 seconds lets the message through and says why: it saves money and never loses a fact. Questions, commands and messages the reader would not read are not gated. One call per message, never again on replay, since a message is handled once. The gate stays off until the owner has run the check: the last few hundred messages Talon holds that the reader would read, one line each with the probability and read or skip, and how many each threshold from 0.2 to 0.4 would let through, with what the check cost.
- **The status check.** After the reader and its own validation, and before anything reaches the tray or the ship, each `status` the reader proposed for a person is put to the decider as a `choice`: circumstance, feeling or neither, one request per message with a question per row under `status_<n>`. The state carries the message, the sender, the proposals and rule 8 of the client guide verbatim. Each question names its own proposal: asked without it, the model cannot tell which of several it means and answers them alike (measured: three different statuses all came back circumstance at 0.7; named, 1.0 circumstance, 1.0 feeling and 0.65 neither). A circumstance at 0.6 or above is kept; a feeling or neither at 0.6 or above is dropped and logged; anything under 0.6 is kept and logged as uncertain. A decider that cannot answer keeps every row. The check never rewrites a value. Situations, things and places keep their own status vocabulary and are not asked about.
- **What the reader sees.** Without help the on-device reader's prompt holds the first 60 bodies, now ranked with the ones the message names first, then people, then activities, places and orgs, then situations, then things. With body picks on, for each message the gate lets through, Jev is asked one noul question per body, in groups of 40 sent together, each call carrying the whole list of bodies, and the reader sees only those scored at or above the cut (0.5 to start), with the sender and the owner always. The list in every call is what makes it work: without it, the bodies a message was plainly about scored with the noise near 0.3; with it they scored 0.8 to 0.96 and the rest 0.06 or less (measured on 173 bodies, about $0.0009 and under a second a message). A pick that fails leaves the reader's list as it was. Like the gate, it stays off until the owner has run the check: Check body picks runs the gate and the picks over 50 messages, shows each message's bodies with their scores, and says how many the reader would see at 0.3, 0.5 and 0.7.
- **What it costs, per day.** Each call logs its input tokens and cost. Each pass adds to the day's tally, kept in `orrery_sent` as `decide:<date>` and logged as two lines: how many the gate read and skipped, and what the gate and the reader cost; and how many statuses were checked, kept, dropped as feeling, dropped as neither, and uncertain.

## 7a. The daily brief

Once a day at 07:00 in the owner's zone (`person/me.timezone`, else America/New_York), the install feeding orrery mails the owner, from the owner, through auspex: subject `Daily brief <date>`, plain text in short lines. It needs a frontier model under AI; without one, or when the ship, the calendar or the model does not answer, nothing is sent and the log says why. The pass loop wakes for seven rather than waiting out its ten minutes; a device asleep at seven sends on waking within the hour, and after that there is no brief that day. A phone's background worker runs every six hours, so on a phone the brief goes out only while the app is open. Only one install pays for a brief. Before the model is called, the install takes the day's lease in the ship's %settings, the same lease scheduled loops use (`claimKey`): it reads the lease, and when it is free or stale it writes its own claim, waits fifteen seconds for rival claims to land, and goes on only if the lease still names it. A holder quiet for twenty minutes, longer than a model call, can be taken over. An install with no way to take the lease (the Android background worker has no %settings channel) sends no brief. A computer contests at seven and a phone at a quarter past, so the two are never in the same contest, and each looks for that day's brief in the mail before the lease and again just before sending.

- **Today.** The calendar's events for the day, all-day first, then by start, times in the owner's zone. A situation whose `starts` is today or an activity whose `next` is today is added only when the calendar has nothing by that title (compared with `normalizeTitle`); a closed or cancelled one is not. Then the open todos: overdue, due today, then undated (ten, and a count of the rest).
- **Waiting on you.** Every proposed action under a tag, `[A1]`, with its kind, what it is about by name, its due and the generator's `why`. The tags are kept with the day in `orrery_sent` (`brief:<date>`), so only the install that sent a brief answers its replies.
- **Suggestions.** The frontier model, given the state laid out as the generator's `build_parts` lays it out (closed, cancelled and over situations left out), the day and the waiting actions, writes at most six lines. It files nothing. The key never reads a sensitive attribute, so none reaches the model.

The owner's reply is read once, keyed on its message id (`reply:<id>`), and recorded only after every write is done. Quoted lines, the attribution and anything after it, and any line the brief itself said are stripped first, so the brief's text is never read back as facts. What is left is read by the same frontier model that wrote the brief, since it changes the state: `common/analyst-prompt.md` word for word, then the reply's own rules, with the brief's tagged actions and the time now in the context. It answers moves, bodies, observations and actions, and each is held to the ship before anything is written. A move names a tag the brief gave, a status of approved, dismissed or done (a proposal is approved on its way to done), a due that parses and a subject of bodies that exist; a new due or subject dismisses the action and proposes a replacement with only the fields `/act` takes, since the action API moves a status and nothing else. Bodies the answer would make are resolved against the ship first; observations are held to the schema's attributes and to bodies that exist, carry conf 100 and source `{"kind": "mail", "id": <reply id>}`. What the owner asks to have done is filed with `/act` when its kind, bodies and required payload keys check out. The reply's words, a health fact included, go to the frontier provider, as the state already does. A reply with no model to read it waits, whole. Every model call's tokens and cost go to the log.

## 8. Surfaces in Talon

- Settings: an Orrery section with the switch, the window for backfill, the channel allow-list, the tray thresholds, the local model's download state, and the cloud switch with its warning.
- The Apps page: an orrery row, install and permits like the others.
- The Noticed tray, in the chat list above Requests, and the same rows reachable from a message's menu.
- The New widget: open orrery actions, so a proposal the analyst made shows beside the mentions. Talon executes `message` (a DM) and `calendar` (an event) kinds with a confirm, reports done or failed, and shows `task` and `note` as the ship's list.

## 9. Phases

1. **Plumbing and the structural pipe.** `OrreryApi`, the probe, the Apps row, key minting, the sync table, contacts, chat and mail last-contact, and calendar situations, batched, backfilled over the window. The switch, off by default.
2. **The funnel and the tray.** Scope, the names gate against the keyed state view, the Noticed tray with its trust rule (a kind of claim confirmed three times and never discarded goes up on its own), a per-channel switch, and a rule-only extractor for the simplest shapes (a status line, "I'm at <place>", a named body's whereabouts) so the tray is useful before the model lands. The embedding pattern gate waits for phase 3: its positive set is the claims the tray has confirmed, and the rules are their own gate until then.
3. **The model ladder.** The floor first, since it is one runtime and one grammar on all three platforms, then each platform's top rung, because that is where most current devices sit: Apple Foundation Models on iOS and macOS, AICore on Android, the local server on desktop. The fixtures, the download, the rung display in Settings, the budget.
4. **Actions back.** Open actions in the New widget, execution of `message` and `calendar`, done and failed.
5. **The middle rungs and the opt-in.** MediaPipe on Android, GPU offload on desktop, and the cloud extractor behind its switch.

## 10. Gates

- Unit: the structural mappers are pure functions from Talon rows to observation JSON, tested against fixtures, including the id alignment with what the ship-side pushes would produce.
- The funnel: a labelled set of messages (claims and chatter) with the expected gate outcome, run on every platform's embedder where one exists.
- Extraction: a fixture set of candidates and expected observations, judged by field match, not by text. It runs in CI against the floor on desktop with a pinned model file, and it is the gate every higher rung must pass, on its platform, before the ladder may select it.
- Against `~wex`: the phase 1 pipe writes, the state view shows it, a resend answers `existing` on every item, and a revoked key answers 403.

## 11. Not in v1

Bodies for groups. Embedding resolve. A second identity on one install. The ship pushing to Talon; the beacon is enough while the app is open.
